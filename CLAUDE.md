## Project Overview

**baseballcoachesapp** is a full-stack coaching platform for high school and youth baseball. It covers five pillars:

1. **Scorekeeping** — offline-first pitch-by-pitch event logging with real-time live score streaming for parents
2. **Communication** — tiered channels (announcement, topic, DM), push notifications, RSVP tracking
3. **Practices** — drill library, drag-and-drop practice builder, multimedia CDN *(v2)*
4. **Administration** — pitch count compliance (NFHS / Little League / NCAA rules), MaxPreps export, FERPA-compliant roster/user management
5. **Statistics** — event-sourced aggregation, Quality At-Bats, spray charts, scouting reports *(v2)*

## Development Workflow

### Branching Strategy

- `main` (or `master`) — stable, production-ready code
- `dev` / `develop` — integration branch for features
- `feature/<short-description>` — individual feature work
- `fix/<short-description>` — bug fixes
- `claude/<task-description>-<session-id>` — AI-assisted work branches

Always branch off `main` (or the designated integration branch) and open a pull request to merge back.

### Commit Messages

Use the [Conventional Commits](https://www.conventionalcommits.org/) format:

```
<type>(<scope>): <short summary>

[optional body]
[optional footer]
```

Common types: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `style`

Examples:
```
feat(roster): add player import from CSV
fix(stats): correct ERA calculation for partial innings
docs: add CLAUDE.md with project conventions
```

### Pull Requests

- Title should match the commit message style above
- Include a description of what changed and why
- Link to any relevant issues
- All CI checks must pass before merging

- TestFlight builds use the `production` profile in `apps/mobile/eas.json` (EAS project `cd5813s-team/baseball-coaches-app`, linked via `app.json` `owner` + `extra.eas.projectId`). Build numbers live on EAS (`appVersionSource: remote`, `autoIncrement`). Ship one with `cd apps/mobile && eas build -p ios --profile production --auto-submit`.

- The iOS deployment target is **15.1** (iOS 13/14 devices are unsupported), set by the `expo-build-properties` plugin in `apps/mobile/app.json` — `ios/` is generated by `expo prebuild` and not committed, so never set it in the Xcode project. App Store Connect rejects uploads targeting below iOS 15.0 from April 2027. The plugin sets the app target and `Podfile.properties.json`; the generated project-level default stays 13.4, which the app target overrides. The target does not cover Apple's separate yearly minimum-SDK rule — that comes from the Xcode in the pinned build image.

## Architecture

**Monorepo** — Turborepo + pnpm workspaces. TypeScript everywhere.

| Layer | Technology |
|-------|-----------|

| Web app | Next.js 14 (App Router) |
| Shared packages | `@baseball/shared`, `@baseball/database`, `@baseball/ui` |
| Backend | Supabase (Postgres + Realtime + Auth + Storage) |
| Offline storage (mobile) | WatermelonDB (SQLite via JSI) |
| Styling (mobile) | NativeWind v4 (Tailwind CSS for React Native) |
| Styling (web) | Tailwind CSS + shadcn/ui |
| Edge functions | Deno (Supabase Functions) |
| Push notifications | Expo Push Notifications |
| Deployment (web) | Vercel |
| Deployment (mobile) | Expo EAS Build |

### Key Architectural Decision: Event Sourcing

`game_events` is an **immutable append-only log**. Every pitch, out, and substitution is a row. Game state (score, count, baserunners) is derived by replaying events. This enables:
- Offline-first sync (events created on device, upserted to Supabase idempotently)
- Full audit trail for pitch count compliance
- Future analytics without schema changes

### RBAC

Roles: `head_coach`, `assistant_coach`, `player`, `parent`, `athletic_director`.
Enforced at three layers: Supabase RLS (primary), edge function JWT verification, client UI gating (cosmetic only).

## Key Conventions

### Code Style

- Prefer **explicit over implicit** — variable names should describe their purpose
- Keep functions **small and single-purpose**
- Avoid deeply nested logic; extract helpers when nesting exceeds 2-3 levels
- Prefer **early returns** over deeply nested conditionals
- Delete dead code rather than commenting it out

### Naming

| Entity | Convention | Example |
|--------|------------|---------|
| Files | kebab-case | `player-stats.ts` |
| Components | PascalCase | `RosterTable` |
| Functions/variables | camelCase | `getPlayerAverage()` |
| Constants | SCREAMING_SNAKE | `MAX_ROSTER_SIZE` |
| Database tables | snake_case | `player_stats` |
| CSS classes | kebab-case | `roster-card` |

### Testing

- Write tests for all business logic (statistics calculations, validation rules, etc.)
- Prefer unit tests for pure functions; integration tests for API endpoints
- Test files live alongside source files or in a dedicated `tests/` directory
- Use descriptive test names that read like sentences: `"should calculate ERA correctly for relief pitchers"`

### Error Handling

- Never swallow errors silently
- Log errors with enough context to debug (include relevant IDs, inputs, etc.)
- Return meaningful error messages to the client; never expose internal stack traces in production
- Validate all external input at system boundaries (API request bodies, user form input)

### Security

- Never commit secrets, API keys, or credentials — use environment variables
- Store sensitive config in a `.env` file (never committed); document required variables below
- Sanitize and validate all user-provided data before using it in queries or responses
- Follow the principle of least privilege for database access and API permissions

## Database

- **Never** modify the Supabase schema manually — always use migrations in `supabase/migrations/`
- Migration files use timestamp prefix: `YYYYMMDDHHMMSS_<description>.sql`
- After adding a migration: run `supabase db reset` locally, then `pnpm --filter @baseball/database gen-types` to regenerate TypeScript types
- **Never** UPDATE or DELETE rows in `game_events` — the table is append-only by design
- After changing `supabase/migrations/`, update `packages/database/src/types/supabase.ts` (or regenerate it)
- The mobile WatermelonDB schema (`apps/mobile/src/db/schema.ts`) is versioned: **never** bump its `version` without adding a matching step in `apps/mobile/src/db/migrations.ts` — a bump without a migration wipes the device database, destroying unsynced offline game events

## Domain Glossary

Consistent naming helps avoid confusion between the codebase and baseball terminology.

| Term | Meaning |
|------|---------|
| **Coach** | A coaching staff member with app access |
| **Player** | An athlete on a roster |
| **Roster** | A list of players for a team or season |
| **Game** | A single scheduled or completed game |
| **Lineup** | The ordered batting order for a specific game |
| **Stats** | Performance statistics (batting, pitching, fielding) |
| **Drill** | A practice activity in a drill library |
| **Season** | A time period grouping games and rosters |
| **GameEvent** | An atomic timestamped action in a game (pitch, hit, out, sub, etc.) — the event sourcing primitive |
| **PitchCount** | Running total of pitches thrown by a pitcher in a game; tracked for compliance |
| **ComplianceRule** | A ruleset (e.g., NFHS, Little League) defining max pitches per day and required rest days |
| **QAB** | Quality At-Bat — a high-school-relevant metric crediting productive plate appearances regardless of traditional hit/out outcome |
| **Channel** | A messaging context: announcement (coach-post-only), topic (threaded), or direct (1:1) |
| **LeagueScoringSettings** | Per-league JSONB blob on `leagues.scoring_settings` that toggles non-standard scoring behaviors (expanded lineups, mercy rule, run cap, guest players, courtesy runners, etc.). Validated by `leagueScoringSettingsSchema` in `@baseball/shared`. |
| **GuestPlayer** | A player appearing in a lineup who is not on the home team's roster — either ad-hoc (free-text name) or an FK to another team's player. Tracked per-appearance via `game_lineups.is_guest` and gated by `settings.guests.allowed`. Creatable offline-first from mobile: RLS policy `coaches_insert_guest_only_players` lets active coaches insert guest-only identities directly, synced via WatermelonDB (`createLocalGuest` in `apps/mobile/src/features/lineup/local-guest.ts`). |
| **LeaguePlayer** | Registry row (`league_players` table) listing every player who has appeared in any team's game inside a league. Seeds the cross-season guest picker. |
| **MercyRule** | League-configurable game-ending rule: `gameLength.mercy = {enabled, runDiff, afterInning}`. The scoring engine surfaces an advisory banner when conditions are met; coach still confirms via End Game. |
| **RunCap** | League-configurable per-half-inning run limit (`gameLength.runCap = {enabled, value}`). Triggers an inning-switch advisory in the scoring UI. |
| **CourtesyRunner** | LL/HS substitution that pinch-runs for catcher/pitcher without burning a regular sub. `SubstitutionType.COURTESY_RUNNER`, gated on `settings.substitutions.courtesyRunnerForCatcherPitcher`. |
| **PlayerTransfer** | Append-only row in `player_transfers` recording a player's move within a league (initial assignment, trade, release, season reassignment). Written by league_admin server actions wrapping `fn_transfer_player` / `fn_release_player`, which also maintain `player_team_memberships` and the `players.team_id` denorm atomically. Coach-driven moves still write to the same table with NULL `league_id`. Does not drive stat attribution — that is derived by joining `game_lineups.game_id → games.team_id` (there is no `team_id` column on `game_lineups`), with guest appearances included/excluded via `count_toward_stats`. |
| **FreeAgent** | A player registered in a league (`league_players` row exists, `is_guest_only=false`) with `players.team_id IS NULL` and no active `player_team_memberships` row. Eligible for assignment to a team via `transferPlayer`. |
| **RunnerOutcome** | A per-runner result on a hit (or other parent play) that diverges from the default auto-advance. Modeled as a separate `BASERUNNER_OUT` (thrown out) or `BASERUNNER_ADVANCE` (held / advanced to a specific base) event whose `relatedEventId` points to the parent play. `deriveGameState` and the stats reducers suppress the parent's default scoring and base placement for any runner referenced by a linked outcome event. Keeps batter hit credit decoupled from runner fate — a double remains a double whether the lead runner scores, holds, or is thrown out. Surfaced in the play feed as a parenthetical on the parent row, e.g. "Double (Alice thrown out advancing, Bob held at 3B)". |
| **StatGroup** | The category a `StatDef` belongs to — `'batting' \| 'pitching' \| 'team' \| 'special'` — declared on every entry in `STAT_CATALOG`. Drives the public league-home **League Leaders** tabs (Batting / Pitching / Team / Special). The default board membership per tab lives in `GROUP_BOARDS` in `apps/web/src/lib/league-home/load.ts`; league-configured custom boards always render under **Special**. |
| **TeamStatPage** | Public read-only page at `/l/[slug]/team/[teamId]` showing a team's record, team-level stats, and full per-player batting/pitching lines. Assembled by `getTeamStatPageData` in `apps/web/src/lib/league-home/team-load.ts` as a `team_id`-filtered view of the existing `league_*_snapshot` tables — no migration, no new aggregation. Reached by clicking any team name on the league page (standings, leaderboards, spotlights, recent results). Opted-out players (`public_opt_out`) render a masked name with blanked (`—`) stat cells for public viewers. The URL builder `teamHref` lives in the non-server-only `team-href.ts` so client components (e.g. `LeaderBoard`) can import it without pulling in the `server-only` loader. The batting/pitching tables are client-sortable by any column (`SortablePlayerTable` + the pure `team-table-sort.ts`); opted-out players' numeric values are stripped to `null` server-side in `toTeamPlayerRows` (not just hidden) so they never reach the client payload, and such rows pin to the bottom of any numeric sort. |
| **DualScorekeeper** | League-wide opt-in (`leagues.scoring_settings.scorekeeping.dualScorekeeper`, default OFF, toggled in League Admin) that lets both teams independently score the same game. Implemented as **paired games**: each team keeps its own `games` row + immutable `game_events` log (no cross-team writes) — the rows are linked via `games.paired_game_id` and each records `games.scorer_side` (`'home'`/`'away'`). The home team's log is canonical. Requires the opponent to be a linked DiamondOS team (`opponent_teams.linked_team_id`); otherwise the toggle is a no-op. `provisionMirrorGame` (`apps/web/src/lib/dual-scorekeeper/provision.ts`) auto-creates the opponent's mirror game on creation. |
| **GameReconciliation** | Append-only `game_reconciliations` row (one per matchup, keyed on `home_game_id`) computed by `runReconciliationForGame` (`apps/web/src/lib/dual-scorekeeper/reconcile.ts`) at End Game **once both paired games are completed**. Diffs the two logs via the pure `reconcileScoreLogs` (`@baseball/shared`) at line-score level (final score, per-half-inning runs, team hits/errors; per-player batting/pitching diffs are supported by the util but await a cross-roster player-identity bridge). Surfaced on the completed-game page via `ReconciliationPanel`. The home team's coach can accept the away value per conflict (`resolved_overrides` JSON, written by `resolveReconciliationConflictAction`); overrides annotate the record and displayed line but never mutate `game_events`. RLS: either paired team reads, only the home coach writes. |
| **LineupSync** | Offline-first two-way sync of `game_lineups` between mobile (WatermelonDB mirror + dedicated lineup screen at `apps/mobile/app/(tabs)/schedule/games/[gameId]/lineup.tsx`) and Supabase. Pull is incremental via `game_lineups.updated_at` (trigger-maintained); push is a per-game whole-lineup replace guarded by the pure `decideLineupPush` in `@baseball/shared`: **mobile wins for `in_progress` games**, last-write-wins by timestamp otherwise (ties favor the device). Server-wins games converge on-device via `applyServerLineupSnapshot`. Web delete-reinserts propagate to devices as deletions via `computeLineupDeletes` (full id-set diff — Postgres has no tombstones). The `league_players` registry also mirrors locally to seed the offline guest picker; the identities themselves arrive via the PII-free `league_player_identities()` RPC (coach-only, no DOB/notes columns) rather than a `players` SELECT policy. |
| **LeagueChannelMembership** | Who is in a league's announcement/topic channels (`league_channel_members`) is derived, not hand-managed: active `league_staff` (admins and managers) with `can_post`, plus active head coaches, assistant coaches and athletic directors of every active `league_members` team, read-only. Players and parents are not members; direct league channels are left alone. Kept current by triggers on `league_channels`, `league_members`, `team_members` and `league_staff` (`supabase/migrations/20261024010000_league_channel_auto_membership.sql`), all funneling through `sync_league_channel_membership(league, user)` and `league_channel_eligible_members(league)`, so app code never inserts channel members itself. `can_post` can only be changed by the service role or those functions (`guard_league_channel_member_can_post`); members still update their own `last_read_at`. |
| **GameRsvp** | Per-game, per-player attendance response (`attending` / `not_attending` / `maybe`) in `game_rsvps`, unique on `(game_id, player_id)`. `user_id` records who responded — the player's own account, or a linked parent (`parent_player_links`) RSVPing on their behalf — authorized by the `public.can_rsvp_for_player` RLS helper; coaches and athletic directors on the game's team read and manage every RSVP. Lazy model: absence of a row means "pending" — the client merges the roster against RSVPs via `summarizeRsvps` (`@baseball/shared`). Surfaced as a button row on the web game detail page (`RsvpButtons.tsx`) and the mobile schedule list (`useGameRsvps` hook), with a coach-only roster view (`AttendancePanel.tsx` on web, `games/[gameId]/attendance.tsx` on mobile). Online-only on mobile — direct Supabase reads/writes, no WatermelonDB mirror. |
| **InviteOnlySignupTrigger** | Postgres `BEFORE INSERT ON auth.users` trigger (`enforce_invite_only_signup`, `supabase/migrations/20260919000000_enforce_invite_only_oauth_signup.sql`, hardened in `20260919010000_harden_invite_only_signup_trigger.sql`) that blocks any non-`email`-provider signup (i.e. Google OAuth) unless the email has a `team_invitations` row with `status IN ('pending', 'accepted')`. Linking a Google identity to an *existing* `auth.users` row (the normal case for an already-invited coach/parent/player) never fires this trigger — Supabase's standard same-verified-email linking only inserts into `auth.identities`. Web reaches this via `/auth/callback` handling Supabase's `?error=server_error` redirect (`apps/web/src/app/auth/callback/route.ts`) → `/login?error=google_not_invited`; mobile via the same check in `apps/mobile/app/(auth)/sign-in.tsx`'s `handleGoogleSignIn`, redirecting through the existing `baseballcoaches://auth-callback` scheme (shared with magic-link, no new scheme). |

| **HitLocation** | Mobile batted-ball capture, gated per game by the GAME_START `hitLocationEnabled` toggle (read as `!== false`, so older events without it default on). Outcome is picked first; the field pop-up (`FieldLocationModal`) opens immediately after, for batted balls only — never for hit-by-pitch or catcher's interference. Payloads carry `sprayX`/`sprayY` (0-1 normalized geometry shared with web's SprayChartPicker as `SPRAY_FIELD` in `@baseball/shared` `rules/batted-ball.ts`) and `fieldingSequence` (first fielder who touched it, then any throws); putouts/assists are credited from it only on outs, per `fielding-stats`. Home runs never record a fielder, and a skipped play writes no batted-ball keys. `react-native-svg` (used by `FieldDiagram`) is a native module — adding or upgrading it needs a native rebuild (`expo run:ios`), not a JS reload. |
| **ScoringTakeover** | A coach can continue on the web (game page → **Continue Scoring**) a game started on mobile. The web scorer reads the mobile GAME_START payload as-is: our starting pitcher falls back to `homeLineupPitcherId`/`awayLineupPitcherId` when no lineup row is marked P, and `hitLocationEnabled` stands in for `sprayChartEnabled`. Like mobile, it records an untracked opponent (no opponent batting order) without an opponent batter/pitcher; our own batter and pitcher are always required (`canRecordPlay` in `apps/web/src/app/(app)/games/[gameId]/score/can-record.ts`). Realtime inserts from the phone bump the web's next sequence number so both can write without colliding on `unique(game_id, sequence_number)`. |
| **TournamentOpponentTeam** | A tournament game scheduled (or edited) with a typed-in opponent gets an `opponent_teams` record linked via `games.opponent_team_id` at that moment, reusing the team's record with the same name case-insensitively (`ensureTournamentOpponentTeam` in `apps/web/src/lib/games/tournament-opponent-team.ts`; earlier games backfilled by `20261020000001_backfill_tournament_opponent_teams.sql`). Mobile mirrors opponent rosters and lineups through that link, so without it a phone-scored tournament game had nothing to sync. Regular games still create it when the web starts the game. |
| **TournamentCreatorSeat** | The creator of a tournament is head coach (and Announcements poster) of the tournament team `create_tournament` makes for **Create Tournament Team**, platform admins included. `prevent_platform_admin_team_membership` still bars admins from every other team, with one exception: a tournament-only team (`tournament_teams.is_tournament_only`) registered to a tournament the admin created (`20261016000003_tournament_creator_head_coach.sql`). The seat matters because web scheduling, lineups, scoring RLS (`game_events`), the tournament lineup guards and the mobile team list all key off `team_members`. Promoting a user to platform admin keeps these seats. |
| **TeamSwitcher (mobile)** | Chip row atop every team-scoped mobile tab — Home, Schedule (games and full schedule), Messages, Stats, Roster and Practices (`apps/mobile/src/features/teams/TeamSwitcher.tsx`) — shown only for users on 2+ teams. It sets RoleProvider's persisted active team, which scopes all of them, and is the path for a coach to reach a separate tournament team's games. Tournament-only teams carry a **Tournament** tag (RoleProvider looks up `tournament_teams` online at hydrate, non-fatal). Tournament games carry the same tag in the games and schedule lists via the existing `games.tournament_id` mirror, with no WatermelonDB schema change. RoleProvider reloads the list in place (no spinner, selection kept) when the sync engine reports a joined or left team. |
| **TeamBackfill (mobile)** | The sync pull is a timestamp window, and joining a team makes its existing rows visible through RLS without touching their timestamps, so the incremental pull alone would never deliver them. Every pull compares the user's active `team_members` teams with the register `sync.knownTeamIds` (WatermelonDB local storage, written in `onDidPullChanges` after the pull is applied, so a failed backfill retries) and re-reads every mirrored table from the beginning for newly joined teams: games, events, lineups, players, channels, messages and opponent players (`apps/mobile/src/sync/team-backfill.ts`, keyset-paged past the PostgREST row cap). A device that synced before the register existed backfills all its teams once. It then calls `notifyTeamMembershipChange()` so RoleProvider reloads the team list. |
| **GameTimeZone** | `games.time_zone` — the IANA zone a game's start time was entered in: the venue's zone (looked up offline from the AddressAutocomplete lat/lng via `@photostructure/tz-lookup`), else the coach's browser zone (hidden `browserTimeZone` field from `BrowserTimeZoneInput`), else the zone already saved on the game (`resolveGameTimeZone` in `apps/web/src/lib/games/game-time-zone.ts`). Web server actions run in UTC, so typed date + time must go through `zonedDateTimeToUtc` (`@baseball/shared`), never `new Date(`${date}T${time}`)`. Every surface renders game times in this zone (`formatDate` / `formatTime` / `formatInTimeZone` / `utcToZonedDateTime` take it as an argument) so web and phones agree; mobile mirrors it in WatermelonDB (schema v5). A game's calendar day for pitch-count and catcher rest is its local day in this zone, not the UTC day (`gameLocalDate` in edge functions, `at time zone` in SQL). Null = unknown; readers fall back to the viewer's zone. |
| **DataAccessRule (mobile)** | How a mobile screen reaches data. If web does the read/write through the user session (RLS) — scoring, lineups, RSVPs, message sends, tournaments, practice attendance — mobile goes **direct to Supabase** (offline-first ones through WatermelonDB). If web uses the service role, admin auth, AI, or a multi-step write, mobile calls a **`/api/m/v1` route** that wraps the same service as the web server action (facility bookings, game notes, opponent lineups and teams, play-by-play corrections, season and league stats, scouting cards, team channel detail/create/delete, message delete and DMs, league channel reads, the practice day, practice planning and the drill library). Never re-implement an authorization rule on mobile; UI gating (`useCan`) is cosmetic. New online-only features use `@tanstack/react-query` (`apps/mobile/src/providers/QueryProvider.tsx`) and add no WatermelonDB tables. |
| **MobileApiLayer** | Bearer-token API for the mobile app under `apps/web/src/app/api/m/v1/` (versioned so a newer app can detect an older web deploy). Routes authenticate with `requireApiUser(req)` (`apps/web/src/lib/api/bearer-auth.ts`: Supabase JWT → `{ user, db: service-role client }` or a 401) and delegate to a **service** in `apps/web/src/lib/services/<area>/` with signature `(db, actorUserId, input: unknown) → ServiceResult` (`lib/services/result.ts`): the service validates `input` with a zod schema from `packages/shared/src/validation/` (so mobile validates with the same one), authorizes the actor, and returns `{ ok, data }` or `{ ok: false, code: invalid | forbidden | not_found | conflict | failed }`. The web server action and the route are both thin wrappers; `serviceResponse` maps codes to 400/403/404/409/500 with a `{ error, code }` body (`failed` hides its message). Reference implementation: `createTeamEvent` (`lib/services/team-events/`) behind `createTeamEventAction` and `POST /api/m/v1/team-events`. Mobile calls the routes with `apiClient` (`apps/mobile/src/lib/api-client.ts`), which throws a typed `ApiError` (`kind`: offline, timeout, unauthenticated, forbidden, not_found, invalid, conflict, server, not_configured, bad_response). `POST /api/games/[gameId]/finalize` predates the prefix but uses the same bearer auth. |
| **MeCapabilities** | `GET /api/m/v1/me` (`apps/web/src/lib/services/me/load-me.ts`), the mobile bootstrap: team memberships (role, own `playerId`, tournament-only flag), each team's subscription `tier` and the `features` it grants (`resolveTeamTier` + `hasFeature`, since `subscriptions` is unreadable through RLS), and active `league_staff` roles. Contract: `meResponseSchema` in `@baseball/shared`. It first runs the same membership/channel self-healing as the web shell (`apps/web/src/lib/membership-self-heal.ts`, shared with `(app)/layout.tsx`). Mobile's RoleProvider publishes the device-cached copy (chunked SecureStore) at cold start, replaces it with a fresh fetch, and falls back to a direct `team_members` read when `/me` is unreachable with nothing cached (tier unknown → no features). It exposes `features` (active team), `leagueRoles`, `isLeagueAdmin`, and `useCan(capability)` — `team.coach`, `team.admin`, `league.staff`, `league.admin`, or any `Feature`. |
| **MobileNavigation** | Five tabs — Home · Schedule · Messages · Stats · More (`apps/mobile/app/(tabs)/_layout.tsx`, Ionicons) — each a nested Stack (`<tab>/_layout.tsx`, shared header in `src/navigation/stack-options.ts`) so details push within their tab. Schedule opens on the games list (the former Games tab) with a segmented control for the full schedule (`?view=all`); scoring, lineup and RSVP screens live at `schedule/games/[gameId]/`. More holds Roster, Practices (the practice day, over `lib/services/practices/` behind `/api/m/v1/teams/:teamId/practices` and `/api/m/v1/practices/:id[/plan|notes|self-notes|cancel|reps|run]`, shared with the web practice actions: upcoming and past practices on a plan with practice planning; coaches log one, edit its plan text, write overall, coach and per-player category notes, log BP reps one tap per outcome with hot/cold hitters from the last 3 days, take attendance, cancel it, and run it block by block — a countdown derived from the block's start time, head coaches and athletic directors start and end it, an assistant controls only the blocks assigned to them, and the runner polls every 15 s so coaches on separate phones stay in step; a player reads their notes and writes their own, a parent reads each child's; block and station structure is built on the web, linked from the app. The top of the list opens the drill library for every member (`/api/m/v1/teams/:teamId/drills`, `/api/m/v1/drills/:id?teamId=`: the curated drills and the team's own, searched and filtered by source and skill category with the shared `filterDrills`, each with the deficits it fixes for the team); coaches add, edit and delete the team's own drills there, never curated ones (`checkCoachOnTeam`, as the web drill actions; an edit replaces every field, so the phone carries over positions, age levels and media links it doesn't show; media links must be http(s)). Its **+** also offers Plan from drills (`…/practices/plan`: when and where, the coach-only plan saved as coach notes, and drills picked from the library that become custom blocks in the order shown), Generate with AI (`/api/m/v1/teams/:teamId/practices/ai-preview` then `/ai`: Claude drafts from the team's drill library, the coach reviews, picks a time and saves), Prep for next game (`…/practice-prep`: a plan from the last completed game's weaknesses and the opponent's tendencies, saved linked to the game, which must be the team's) and Templates (`…/practice-templates`, `/api/m/v1/practice-templates/:id/duplicate|archive`); a practice offers its AI post-practice summary to coaches (`/api/m/v1/practices/:id/summary`) and Apply a template to head coaches and athletic directors before it starts (`…/apply-template`, which replaces its blocks). All over `lib/services/practices/` (`ai-practice`, `prep-practice`, `practice-summary`, `practice-templates`), shared with the web pages and actions; the AI calls get a long client timeout and need `ANTHROPIC_API_KEY` on the web host), Facilities (week view of bookings; coaches book and manage), Opponents for coaches (the team's opponent teams and rosters, `/api/m/v1/teams/:teamId/opponent-teams` and `/api/m/v1/opponent-teams/:id`, over `lib/services/opponent-teams`, and each team's AI scouting card, `…/scouting-card`, whose POST waits on the model and so gets a long client timeout), league/web links and Account; a game in progress opens the read-only live viewer (`schedule/games/[gameId]/live`, a Supabase Realtime subscription on `game_events`) for anyone not scoring; Messages lists the team's channels from WatermelonDB, hiding topic channels and DMs the plan lacks (`visibleChannels`), and its **+** offers New channel (coaches) and New direct message (`messages/new`, `messages/new-dm`); an open channel loads its detail from `GET /api/m/v1/channels/:id` (display name, can-post, member role badges; marks it read), syncs on Realtime message INSERT/UPDATE (`use-channel-realtime.ts`), and lets a sender or coach long-press delete a message and a coach delete a non-DM channel (removed from the device at once by `removeChannelLocally`), all over `lib/services/messaging/team-messaging.ts`, shared with the web actions. The sync pull also removes messages soft-deleted since the last pull (`message-deletions.ts`). Above the team's channels, Messages lists the league channels of the team's league the user is a member of (`GET /api/m/v1/teams/:teamId/league-channels`, `LeagueChannelSection`); one opens online-only at `messages/league/[channelId]` (`GET /api/m/v1/league-channels/:id`, over `lib/services/messaging/league-messaging.ts`, read with the service role because RLS on `user_profiles` hides names across teams), refetches on Realtime `league_messages` changes, and lets members with `can_post` post by a direct insert under RLS. Today only league admins and staff are ever added to league channels, so coaches see none; Stats shows the season (pitching with rest and 7-day counts, hitting, catcher, opponents on plans with opponent tracking) from `GET /api/m/v1/teams/:teamId/stats`, the web Stats page's loader (`loadTeamSeasonStats`), with column visibility, totals and rest status shared through `season-stat-columns` in `@baseball/shared`; coaches open the Bullpen Planner (`stats/bullpen`, `…/bullpen?date=`) from it; in a league on a plan with opponent tracking (where the web links League Stats) it links League Stats and Team Comparison (`stats/league`, `stats/league-teams`; `…/league-stats`, `…/league-comparison`, over `loadLeaguePlayerStats` / `loadTeamComparison` in `apps/web/src/lib/stats/`, shared with the web pages). `app/auth-callback.tsx` handles the `baseballcoaches://auth-callback` magic-link deep link.
